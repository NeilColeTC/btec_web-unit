# Student Project Structure – Guidance Template

## Purpose

This template suggests an **evidence organisation structure**, not a completed assignment structure or starter solution.

Learners may adapt the organisation to suit the approved submission method. The important outcome is that evidence is clear, authentic and traceable.

```text
student-project/
├── 01-requirements-and-planning/
├── 02-designs/
├── 03-design-review-and-refinement/
├── 04-website/
├── 05-development-evidence/
├── 06-testing/
├── 07-optimisation/
├── 08-evaluation/
└── evidence-index.md
```

## 01 – Requirements and planning

Possible evidence:

- learner interpretation of the client brief;
- problem definition;
- intended audience/user needs;
- explicit and inferred requirements kept clearly distinct;
- constraints;
- success criteria;
- initial project/milestone planning.

## 02 – Designs

Possible evidence:

- site map;
- mood board/style direction;
- wireframes;
- responsive design ideas;
- alternative designs;
- asset plan;
- SEO plan;
- pseudocode/flowcharts where relevant;
- annotations linking decisions to requirements.

## 03 – Design review and refinement

Possible evidence:

- review records;
- reviewer feedback;
- accept/adapt/reject decision records;
- before/after designs;
- learner justification of final design decisions.

## 04 – Website

The actual learner-developed website and its required assets.

Keep paths portable. The project should not depend on files elsewhere on the learner's computer.

## 05 – Development evidence

Possible evidence:

- development screenshots where they demonstrate meaningful stages;
- relevant code extracts with explanation;
- debugging records;
- requirement-to-implementation traceability;
- version/change history;
- compatibility checks carried out during development.

A large unexplained code dump is not a substitute for evidence of process and reasoning.

## 06 – Testing

Possible evidence:

- test plan;
- expected and actual results;
- normal/boundary/erroneous data where appropriate;
- compatibility/responsive/usability/accessibility checks;
- defects;
- fixes;
- retests;
- regression checks.

Preserve genuine failures. They can provide valuable evidence of development and improvement.

## 07 – Optimisation

Possible evidence:

- issue identified from testing/feedback;
- priority/reason for improvement;
- alternatives considered;
- before evidence;
- change made;
- after evidence;
- comparable retest;
- learner judgement about whether the change worked.

## 08 – Evaluation

The final evaluation should use the learner's own evidence to judge:

- fitness for purpose;
- success against client requirements;
- suitability for the intended audience;
- design and usability;
- responsive behaviour and accessibility;
- functionality and scripting;
- compatibility/performance where tested;
- testing and optimisation outcomes;
- limitations, trade-offs and realistic improvements;
- effectiveness of working practices.

## Evidence index

A useful final index can contain:

| Evidence item | Location | What it demonstrates |
|---|---|---|
| | | |
| | | |
| | | |

The index helps another person follow the project. It should describe existing evidence, not make unsupported claims about criterion achievement.

## Evidence integrity

Do not recreate a fictional development history at the end of the project. If an artefact was never produced, record the gap honestly. Organising existing evidence is appropriate; fabricating historical reviews, tests, screenshots or timestamps is not.

## Assessment boundary

This folder structure supports organisation only. It intentionally contains no Hot Beans wireframes, code, testing results, optimisation decisions or assignment-ready evaluation.
