# Week 4 Teacher Guidance – Website Performance and Evaluation

## Curriculum purpose

Week 4 closes the taught content for Learning Aim A. The session should consolidate A1 and A2 while making the assessment-language progression explicit:

**compare → analyse → evaluate**

The most important outcome is not memorising isolated performance terms. Learners should understand how technical factors influence the user experience and how that experience can affect whether a website meets audience, purpose and client requirements.

## Specification coverage

### A2 performance factors

Ensure learners can explain:

- where scripts run: server-side or client-side
- browser compliance
- server-side factors: bandwidth availability, number of hits and file types
- client-side factors: upload/download speeds, browser, cache memory, processor speed and interactivity

### Consolidation of A1

Continue linking performance to:

- usability
- navigation
- media
- accessibility
- creativity
- SEO
- audience and purpose

## Indicative retrieval answers

1. Purpose = what a website is intended to achieve; audience = the users it is designed for.
2. Accept valid A1 principles such as usability, layout, accessibility, navigation, typography, consistency, content or simplicity.
3. White space is intentionally unused space around or between elements.
4. Accessibility affects whether users with different needs can perceive, understand and use the site.
5. SEO aims to improve discoverability in search engines.
6. Indexing is the process by which search engines record and organise information about pages for retrieval in search results.
7. Client-side processing occurs on the user's device/browser; server-side processing occurs on the web server.
8. Examples include large images, video, animation or other media with significant file sizes.
9. Browser compliance means website features work appropriately across supported browsers.
10. Comparison identifies similarities/differences; analysis explains how and why they matter.
11. Evaluation adds supported judgement about effectiveness/significance, considering evidence and limitations.
12. Evidence makes a judgement defensible rather than simply personal opinion.

## Performance-scenario guidance

### Breaking news
Most relevant: number of hits, bandwidth/server capacity. Learners may also discuss server-side processing load. Encourage them to explain the chain from demand to slower response rather than simply naming “traffic”.

### Large image gallery
Relevant: file types/file size and download speed. Solutions could include resizing, compression, more suitable formats or loading strategies. Avoid teaching that the smallest possible file is automatically optimal; image quality and purpose matter.

### Browser problem
Relevant: browser compliance/compatibility. The impact is reduced functionality or usability for affected users.

### Returning visitor
Relevant: cache memory. Previously downloaded resources may be loaded locally, reducing repeat transfer.

### Older laptop
Relevant: processor speed and client-side workload. Complex effects or scripts may perform poorly on lower-powered devices.

### Product video
Relevant: file size/download speed/interactivity. This is a useful trade-off example because richer media may improve engagement while worsening performance for some users.

### Busy application portal
Relevant: number of hits and bandwidth/server-side capacity.

### Interactive form
Relevant: processor speed, client-side scripting and interactivity. Strong answers should distinguish useful functionality from its possible processing cost.

## Teaching organisational impact

Keep organisational impact grounded in user consequences. A useful model is:

**website feature/performance issue → user experience → user behaviour → organisational consequence**

For example, do not accept “slow website = lost money” without explanation. Ask:

- What user task is affected?
- What might the user do?
- Why does that matter to the organisation?
- Is that consequence certain or merely possible?

This helps learners avoid overclaiming.

## Compare → analyse → evaluate

### Pass-level thinking

Learners identify and compare website-design principles and their suitability.

### Merit-level thinking

Learners explain how design principles produce creative, high-performance websites that meet client requirements.

Key prompt: **How and why does this evidence matter?**

### Distinction-level thinking

Learners evaluate effectiveness by weighing evidence, consequences, strengths, limitations and trade-offs before reaching a supported judgement.

Key prompt: **So, how effective is it overall, and why?**

Avoid presenting these as rigid paragraph formulas. The structures are scaffolds for reasoning, not templates to mechanically fill.

## Modelling boundary

Use a neutral website pair for detailed worked examples. BBC and Amazon are the planned course comparators for Assignment 1, so do not provide complete assignment-ready analysis or evaluation of those websites.

You can still question learners about their observations:

- What evidence supports that?
- What does that mean for the user?
- How does that relate to purpose?
- What is the performance implication?
- What is the limitation?
- What judgement follows?

## Common misconceptions and interventions

### “Server-side means slow”
Explain that location of processing alone does not determine speed. Performance depends on workload, infrastructure, connection and implementation.

### “More bandwidth fixes everything”
Ask learners to consider client connection, browser, processor, file choices and script complexity.

### “A large image is bad”
Ask what the image is for, what quality is required and whether an optimisation could preserve purpose while reducing cost.

### “Evaluation means pros and cons”
A list is not enough. Require learners to decide which evidence matters most and reach a supported conclusion.

### “Distinction means more writing”
Refocus on quality of judgement, balance and evidence rather than length.

## Adaptive teaching

### Support

- teach factors using server-side/client-side sorting
- provide one-variable scenarios before multi-factor examples
- use chain diagrams
- provide sentence stems: “This affects… because… which means…”
- use a paragraph scaffold for evaluation
- let learners verbalise reasoning before writing

### Stretch

- introduce competing explanations for one performance issue
- ask learners to rank factors by likely significance
- require contextual judgement for different devices/users
- challenge overconfident causal claims
- ask learners to explain why optimisation may involve trade-offs

## English, maths, EDI and employability

**English:** comparison, analytical explanation, evaluative judgement and evidence-led conclusions.

**Maths:** bandwidth, file size, transfer rates and proportional changes provide natural numeracy links. Keep calculations meaningful to the concept being taught.

**EDI:** make explicit that performance can exclude users with slower connections, older hardware or assistive technologies.

**Employability:** performance diagnosis, quality assurance, testing mindset, client communication and evidence-based recommendations.

## End-of-Learning-Aim-A diagnostic

Before learners move into Assignment 2, check whether they can independently:

1. identify specific website evidence
2. explain the relevant principle or performance factor
3. connect it to audience/purpose/client requirements
4. analyse consequences
5. reach a balanced judgement

Learners unable to do stages 4–5 need targeted writing support before finalising Assignment 1.
