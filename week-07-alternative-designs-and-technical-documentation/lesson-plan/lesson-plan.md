# Week 7 Lesson Plan – Alternative Designs and Technical Documentation

**W/B:** 19 October 2026  
**Duration:** 3 hours  
**Specification focus:** B1–B2  
**Assessment preparation:** B.P2, B.P3, B.M2

## Learning outcomes

Learners will be able to:

1. Distinguish genuine design alternatives from superficial variations.
2. Develop mobile/tablet alternatives that respond to device constraints.
3. Plan SEO features and digital assets.
4. Write pseudocode for intended JavaScript behaviour.
5. Represent a simple interaction with a BCS-style flowchart.
6. identify copyright and data-protection implications.
7. Compare options against user needs, purpose and constraints.
8. Produce technical documentation that supports later development and justification.

## Teacher modelling

Use a neutral scenario rather than Hot Beans Web for complete worked models. Demonstrate this sequence:

1. identify a requirement
2. propose two viable alternatives
3. identify a technical or user constraint
4. compare consequences
5. choose one option
6. justify the choice

For scripting, model a simple neutral interaction such as validating a newsletter sign-up field rather than supplying assessed Hot Beans code logic.

## Adaptive teaching

### Support

- provide one completed neutral alternative-design example
- use a comparison table with prompts for audience, purpose, usability and feasibility
- provide pseudocode stems: INPUT, IF, ELSE, DISPLAY
- provide a flowchart-symbol key
- reduce the number of planned interactive features initially
- use an asset register with pre-defined columns

### Stretch

- require learners to compare two technically feasible alternatives with different trade-offs
- ask for responsive behaviour at more than one viewport width
- include accessibility/performance consequences in design choices
- require pseudocode with multiple decisions or validation rules
- require learners to explain how asset/licensing decisions affect implementation

## English and mathematics

**English:** concise technical annotation, comparison, justification, technical vocabulary and writing unambiguous pseudocode.

**Mathematics:** dimensions, proportions, responsive scaling, relative sizing and logical decision structures.

## EDI / British Values / employability

Accessibility and inclusive responsive design should remain part of each decision. Copyright and data protection reinforce rule of law and responsible professional practice. Technical documentation, decision-making and traceability mirror real web-development workflows.

## Misconceptions to anticipate

- changing only colour creates a meaningful alternative design
- responsive design means shrinking the desktop page
- SEO is only keywords
- any image found online can be used if credited
- pseudocode must use exact JavaScript syntax
- flowcharts are decorative rather than logical planning tools
- data protection only matters after a form is built

## Assessment boundary

Learners can be taught methods, terminology, checklists and neutral worked examples. Do not provide completed assessed alternatives, pseudocode, flowcharts or legal justifications for Hot Beans Web.

## After the lesson

Check that every learner has enough design evidence to participate meaningfully in Week 8's two-person design review. Identify missing alternatives, technical documentation or traceability before feedback is gathered.
