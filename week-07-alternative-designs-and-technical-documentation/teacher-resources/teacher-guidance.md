# Week 7 Teacher Guidance – Alternative Designs and Technical Documentation

## Curriculum purpose

Week 7 completes the main design-production phase before formal review. Learners should leave with sufficiently developed alternatives and technical documentation to enable meaningful feedback in Week 8.

The core progression is:

**requirement → alternative → technical plan → constraint → decision → justification**

## Specification coverage

Ensure learners encounter and apply:

- alternative design ideas/prototypes
- mobile/tablet compatibility
- SEO planning
- asset planning
- pseudocode
- flowcharts using BCS-standard symbols
- ready-made/original assets
- copyright considerations
- data-protection considerations
- technical/design constraints

## What counts as a genuine alternative?

A strong alternative changes a meaningful design decision such as structure, navigation, hierarchy, interaction or responsive behaviour. A simple colour or font swap is generally too weak unless the change is part of a broader design rationale.

## Responsive-design guidance

Push learners beyond 'make it smaller'. Good responsive reasoning may include:

- changing column structure
- reprioritising content
- collapsing navigation
- changing image sizing/cropping
- increasing touch-target sizes
- simplifying non-essential elements

Require learners to explain why each change helps the intended audience.

## SEO guidance

Keep this practical and implementation-oriented. Useful planning includes page titles, headings, relevant wording, metadata, meaningful link text and accessible image text. Avoid teaching SEO as keyword repetition.

## Pseudocode and flowcharts

The purpose is planning intended behaviour, not assessing a programming language syntax exercise.

A suitable neutral model might be:

```text
START
INPUT email
IF email is empty THEN
    DISPLAY error
ELSE
    DISPLAY confirmation
END IF
END
```

Then show how the decision becomes a branching flowchart.

Learners' assessed technical documentation should relate to interaction they genuinely intend to implement.

## BCS-style flowchart expectations

At this level, focus on correct use of core symbols:

- terminator for start/end
- process for processing/action
- decision for branching
- input/output where appropriate
- directional flow lines

Do not overcomplicate notation if the intended interaction is simple.

## Asset planning and copyright

Learners should record provenance rather than relying on memory. A useful asset register includes source, creator/owner, permission/licence and file type.

Key misconception: crediting an image is not automatically permission to use it.

## Data protection

Connect the topic directly to the planned application form. Encourage learners to question whether each field is necessary and what purpose the data serves. The design stage is the correct point to consider this rather than treating it as an afterthought.

## Assessment boundary

Tutor modelling should use a neutral website brief. Do not create completed Hot Beans Web alternative designs, scripts, flowcharts or legal justifications for learners.

## Indicative retrieval answers

1. A client requirement is something the client says the website must achieve/include.
2. A design constraint limits possible solutions.
3. Examples: site map, mood board, wireframe, page layout.
4. A site map represents page/site structure and relationships.
5. A wireframe represents layout/content placement before visual detail.
6. Annotation explains rationale and links choices to needs/requirements.
7. Responsive design adapts layout/interaction to different viewport/device contexts.
8. Examples: collapsed navigation, stacked columns, resized media.
9. SEO is planning/optimising content and structure so pages can be found and understood by search engines/users.
10. An asset is a media/resource used in the website.
11. Sources should be recorded to establish provenance, permission/licensing and accountability.
12. Pseudocode plans logic without requiring exact programming syntax.
13. Example: diamond = decision.
14. Copyright affects whether assets may legally be used/modified.
15. Forms collect personal data, so what is collected and why should be considered.

## Common weak responses

### 'My alternative uses blue instead of green.'
Ask: what meaningful user experience or structural decision has changed?

### 'Mobile will be the same but smaller.'
Ask: what happens to navigation, columns, images and touch controls?

### 'I will use images from Google.'
Ask: who owns them and what gives you permission to use them?

### 'The JavaScript will validate the form.'
Ask: what exact inputs are checked, what decisions occur and what feedback is shown?

## Preparing for Week 8

Before the session ends, learners should have enough material for reviewers to inspect:

- original design(s)
- at least one meaningful alternative
- responsive considerations
- SEO plan
- asset plan
- scripting logic
- legal/ethical notes

Week 8 feedback is only useful if reviewers have concrete evidence to evaluate.
