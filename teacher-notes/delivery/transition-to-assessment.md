# Transition to Assessment

## Purpose

This document describes how to close the Hot Wheels teaching exemplar and move learners into independent assessed Hot Beans Web work without allowing the exemplar to become a disguised starter template.

## The transition point

The transition should occur after learners have:

- investigated the three exemplar stages
- experimented with HTML, CSS and JavaScript techniques
- completed at least some debugging/testing work
- considered optimisation and accessibility
- reflected on which techniques are appropriate in different contexts

At this point, stop developing Hot Wheels.

Use `learner-activities/now-build-yours.md` as the learner-facing exit activity.

## Make the boundary explicit

A useful teacher message is:

> Hot Wheels was one example of a development process. Your assessed website must now be driven by the Hot Beans client brief, your own design decisions and your own implementation evidence.

The intended transfer is:

**knowledge + reasoning + method**

not:

**layout + code + content structure**

## First activities after the boundary

Return to the approved Hot Beans brief and ask learners to work from the client requirements rather than from the exemplar code.

Appropriate early tasks include:

- requirements analysis
- identification of intended users
- site map/content planning
- alternative design ideas
- wireframes/prototypes
- consideration of technical constraints
- planning appropriate client-side functionality
- initial test planning

Do not begin by asking learners which Hot Wheels features they will copy.

## Technique transfer discussion

A useful transition exercise is to ask learners to classify exemplar techniques:

| Technique | Definitely appropriate? | Possibly appropriate? | Probably unnecessary? | Reason based on client requirements |
|---|---|---|---|---|
| Responsive navigation | | | | |
| Grid layout | | | | |
| Flexbox | | | | |
| Form validation | | | | |
| Theme preference | | | | |
| Local storage | | | | |
| Scroll-to-top | | | | |
| Responsive imagery | | | | |

There should be no expectation that every technique is selected.

A justified decision not to use a technique can demonstrate stronger understanding than including a feature without purpose.

## Assessment-support boundary

During assessed development, support should remain consistent with the approved assignment and centre assessment practice.

The exemplar may have taught learners how techniques work, but assessed evidence should reflect their own:

- interpretation of requirements
- design choices
- assets/content
- responsive decisions
- scripting decisions
- testing
- feedback response
- optimisation
- evaluation

Avoid turning Hot Wheels into a side-by-side blueprint for the assessed solution.

## Evidence of independence

Useful signs that a learner has transferred learning independently include:

- their site structure differs because their client requirements differ
- visual design is justified from audience/purpose rather than inherited from the exemplar
- selected JavaScript solves a need in their own solution
- they can explain why a technique was chosen
- test cases arise from their own requirements/features
- improvements respond to their own evidence and feedback

## Warning signs

Potential indicators that the exemplar is being used too directly include:

- page structure copied with labels/content simply renamed
- identical layout hierarchy without client-led justification
- every Stage 3 JavaScript feature appearing regardless of need
- matching breakpoints/colours/components with no explanation
- testing copied from exemplar resources without being adapted to the learner's actual implementation

If these occur during teaching, redirect discussion back to the learner's own requirements and design rationale.

## Final learner question

A useful independence test is:

> If the Hot Wheels exemplar were unavailable, could you still explain and continue developing your own solution?

The goal of the teaching sequence is for the answer to be yes.
