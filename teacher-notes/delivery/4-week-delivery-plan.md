# Four-Week Delivery Plan

## Purpose

This plan describes a suggested four-week teaching journey using the Hot Wheels exemplar before learners return to their independent assessed Hot Beans Web work.

It is deliberately a delivery framework rather than a minute-by-minute lesson plan. Teachers should adapt timings and depth to the needs of their group.

## Core principle

The exemplar should be released progressively.

```text
CLIENT BRIEF
     ↓
Interpret requirements
     ↓
STAGE 1 — HTML
     ↓
Investigate & modify
     ↓
STAGE 2 — CSS
     ↓
Compare, experiment & justify
     ↓
STAGE 3 — JavaScript
     ↓
Investigate, break & debug
     ↓
TEST + OPTIMISE
     ↓
EXIT THE EXEMPLAR
     ↓
──────────────────────────
     ASSESSMENT BOUNDARY
──────────────────────────
     ↓
HOT BEANS CLIENT BRIEF
     ↓
Independent planning
     ↓
Independent development
```

## Week 1 — Requirements, structure and semantic HTML

### Learning intentions

Learners should be able to:

- interpret a fictional client brief
- identify suitable pages and content
- explain the role of semantic HTML
- trace navigation and relative links
- identify meaningful headings, images, alternative text and form controls
- distinguish structure/content from presentation

### Repository release

Release:

- `client-brief/hot-wheels-exemplar-brief.md`
- `stage-1-html-foundation/`
- selected learner activities only after initial interpretation

Do not release Stages 2 or 3 yet.

### Suggested sequence

1. Analyse the fictional Hot Wheels brief before showing any exemplar code.
2. Ask learners to predict page structure, navigation and content requirements.
3. Reveal Stage 1 as one possible implementation.
4. Compare learner predictions with the exemplar.
5. Investigate semantic structure, metadata, links, images, alt text and forms.
6. Make controlled HTML-only changes.
7. Finish with a small independent HTML extension or critique task.

### Suggested evidence of learning

- annotated brief
- proposed page/site structure
- code investigation notes
- modified HTML experiment
- short explanation of why semantic structure matters

## Week 2 — CSS, layout and responsive design

### Learning intentions

Learners should be able to:

- explain separation of structure and presentation
- identify appropriate selectors and reusable CSS rules
- compare Flexbox and Grid
- explain responsive behaviour and media queries
- recognise focus/hover states and accessibility considerations
- justify design choices rather than copy values mechanically

### Repository release

Release:

- `stage-2-responsive-design/`
- `learner-activities/stage-comparison.md`
- `learner-activities/design-decisions.md`
- `learner-activities/accessibility-audit.md`

### Suggested sequence

1. Revisit Stage 1 and identify presentation/usability limitations.
2. Reveal Stage 2.
3. Learners investigate differences before direct explanation.
4. Teach selectors, box model, custom properties, Flexbox, Grid and media queries through discovered examples.
5. Run a breakpoint experiment.
6. Audit accessibility and keyboard/focus behaviour.
7. Ask learners to justify one design decision and propose an alternative.

### Suggested evidence of learning

- completed Stage 1 → Stage 2 comparison
- breakpoint experiment
- design-decision justification
- accessibility findings

---

## Week 3 — JavaScript and purposeful interaction

### Learning intentions

Learners should be able to:

- identify a user/interface problem that JavaScript can solve
- explain events, functions, parameters, decisions and iteration in context
- identify DOM manipulation and browser storage
- explain defensive checks in shared scripts
- understand progressive enhancement
- use developer tools to diagnose simple faults

### Repository release

Release:

- `stage-3-javascript-refinement/`
- Stage 2 → Stage 3 section of `stage-comparison.md`
- `learner-activities/debugging-challenges.md`
- optional `learner-activities/extension-challenges.md`

### Suggested sequence

1. Begin with Stage 2 and ask what useful behaviours are still missing.
2. Reveal Stage 3 and identify new features before reading the script.
3. Connect visible behaviours to programming constructs.
4. Disable JavaScript and examine what remains usable.
5. Discuss progressive enhancement.
6. Complete controlled code experiments.
7. Finish with debugging challenges using temporary copies.

### Suggested evidence of learning

- annotated JavaScript examples
- Stage 2 → Stage 3 comparison
- debugging record showing symptom → diagnosis → fix → retest
- short explanation of one purposeful JavaScript feature

---

## Week 4 — Testing, optimisation and independent transfer

### Learning intentions

Learners should be able to:

- plan systematic tests against requirements/features
- distinguish expected and actual results
- record defects and retesting evidence
- investigate performance and image optimisation
- evaluate whether a change is genuinely an improvement
- transfer techniques independently to a different client problem

### Repository release

Release:

- `learner-activities/testing-workbook.md`
- `learner-activities/performance-investigation.md`
- `learner-activities/now-build-yours.md`
- relevant learner resources on testing and optimisation

### Suggested sequence

1. Ask: "Is Stage 3 finished? How do we know?"
2. Build a test plan before testing.
3. Execute tests and record failures as useful evidence.
4. Investigate page weight and image optimisation.
5. Make a justified change and retest.
6. Evaluate the evidence.
7. Explicitly close the Hot Wheels exemplar.
8. Return learners to the approved Hot Beans brief and independent design decisions.

### Suggested evidence of learning

- test plan and results
- defect/retest record
- optimisation comparison
- final reflection on which techniques may or may not transfer to another client

## End state

By the end of Week 4, learners should understand the exemplar's techniques and development process but should no longer be treating Hot Wheels as a template for the assessed website.

The teaching objective is successful transfer of knowledge and method into an independently designed client solution.
